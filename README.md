## 🌟 插件简介

战队对战战报是一个面向 QQ 群聊的**约战排表与战报统计**插件：群内一键随机排表，成员在群里填比分，机器人负责解析入库，并给出个人积分榜、队伍对战记录、胜率走势图和数据导出。**友谊赛与踢馆**都支持，告别手工记账和 Excel 统计，让每一次约战都有据可查！（

数据存储于 MySQL 8.0.19+（本次验证为 8.4），支持同一战队多个群合并统计。

本次审查的问题、修复与尚存限制见 [代码审查报告](CODE_REVIEW.md)。

## 🎴 核心功能

机器人的固定回复使用**猫娘口吻**（中等浓度：句尾「喵」/「喵～」，关键回执配一个颜文字）。语气只加在**叙述句**上——表格表头、面板标签、命令语法、战报模板与逐场数据行保持原样，方便直接复制使用。AI 点评使用插件统一人格自由发挥，插件不强制猫娘口吻。

### 📋 排表 (/排表)
- 按 `队伍名: 成员1 成员2` 提供名单，随机配对生成第一轮战报模板
- 第一行可写规则（如 `人头赛`），不写则用默认规则 `2/3【KOF】`
- 人数不等时，人少的一侧以 `TK` 占位，替换为实际玩家名即可
- 排表、记录比分、追加轮次生成的完整战报直接以纯文本发送，保持 `玩家A  2:0  玩家B` 的双空格分隔；选手 ID 内部的空格保持原样。
- 也可 @机器人说“帮我排表，a队是云玩家和萌新，b队是遗老和鸽子”，由 AI 调用排表工具；规则未指定时使用插件默认值。

#### 让 AI 调用排表

插件已注册 AstrBot 工具 `battle_report_lineup`。在 AstrBot 工具管理中确认它已启用；如果当前聊天人格限制了工具名单，将它加入可用工具。当前对话模型需要支持工具调用，使用 AstrBot 当前会话的模型和人格，无需另配插件模型。

提供双方队名、完整名单及需要的规则即可。工具与 `/排表` 共用群禁用、数据库检查和名单解析，只在当前群生成今日第一轮模板；不要求先绑定战队或群属性，不提交战报。带空格的 ID 可以按原样提供给 AI，工具参数中仍用引号保护。成功后直接发送可复制原文，结束本轮工具输出，避免模型重写双空格。


### 按平台分配战报指令

在插件配置的“平台指令配置”中新增一条配置，填写名称和机器人连接 ID，再选择“仅开放勾选指令”“全部开放”或“全部屏蔽”。连接 ID 使用对应机器人 `/sid` 回执中的 Bot ID；同一种接入下的多个机器人也能分别设置。

指令通过多选框分配，别名共用同一权限；“第N轮”涵盖第二轮等追加轮次，“排表”同时控制 AI 排表工具。同一连接匹配多条时最上面的配置生效，空连接列表不生效；未配置的连接保持原范围。被屏蔽的指令在参数解析前静默跳过，不转给默认 LLM，也不阻止其他插件。

开放仍需满足原有身份和群权限。等车仅 QQ 官方可用，原 QQ 确认/解除、申请处理及群成员导出等仍保留 OneBot 要求；普通聊天规则不变。详见[平台指令配置指南](PLATFORM_COMMAND_GUIDE.md)。

### QQ 双机器人命令隔离

同群同时部署 QQ 官方机器人和 SnowLuma 时，在两边的 AstrBot 配置中均启用本插件。QQ群里以 `/` 开头的消息只交给插件处理：当前机器人未启用相应功能时，不再自动转成 AI 对话。

不带 `/` 的形式按 AstrBot 已注册命令及别名识别，包括当前连接未启用的插件指令。已经启用的插件仍照常执行，插件自己的 AI 功能不受影响；未注册的自定义裸指令建议加 `/`。SnowLuma 普通聊天继续沿用原唤醒规则，无需配置 `chat` 前缀；私聊保持原流程。官方端默认仅等车，可按平台配置开放其他指令；默认聊天仍保持静默。

### 🔎 战报核对 WebUI

在 AstrBot 后台的插件详情页打开“战报核对”，按战队和月份抓取外部战报站记录，查看匹配、缺失、重复、胜负与内容差异，并排核对原文。支持查询地址导入、进度、取消、历史及JSON导出。“本地战报”为第一个、默认打开的 Tab，“战报核对”第二、“云端战报”第三。列表直接展示完整战报，每份旁边的“复制全文”可直接复制换行和空格；可跨页勾选后批量私聊发送给自定义 QQ 或目标战队的指定管理员。网站记录按云端 ID 存入独立表，重复拉取更新原记录；本地战报与统计保持不变。详见[使用说明](REPORT_COMPARISON_GUIDE.md)。

安装／更新插件后自动注册独立入口，在现有 AstrBot 访问地址后添加 `/battle-report/` 即可，使用原管理员账号登录。无需导出文件、新增端口或配置 Nginx。可选独立域名等部署方式见 [独立入口部署指南](STANDALONE_WEBUI_GUIDE.md)。

### 🚗 QQ 官方机器人友谊等车

仅 QQ 官方群聊可用，需要 Markdown、动态按钮和群主动消息权限。本插件在官方端默认仅开放等车，可通过平台指令配置开放其他功能；音乐等其他插件照常处理自己的命令，普通聊天不触发 AstrBot 默认 AI 回复；SnowLuma 保留原功能，等车相关指令在 SnowLuma 下无响应。

| 操作 | 指令 / 按钮 |
|---|---|
| 创建或查看所有队伍 | `/友谊等车` |
| 加入队伍 | “进队等车”或 `/进队等车 [车号]`；点车次旁的文字可填入指定队伍 |
| 离开自己所在队伍 | “跑路了再见”或 `/离队`，无需车号 |
| 告知目的群号并结束该车 | “发送群号”，补上群号再发送；`/发送群号 123456789` |
| 新增独立队伍 | “再开一车”或 `/再开一车` |
| 解散自己所在队伍 | “解散队伍”或 `/解散`，无需车号，仅本车成员可操作 |
| 关联原账号 | `/等车ID "示例 玩家"`；原 QQ 在 SnowLuma 用 `/确认关联 确认码` 确认 |
| 查看操作流程 | `/等车帮助`、`/帮助 等车` |
| @全体成员摇人友谊 | “呼叫全体”或 `/呼叫全体`，同群冷却30分钟 |

- 入队后自动识别本人队伍：`/离队`、`/解散` 都不填车号，`/发送群号 123456789` 只填目的群号。只有加入指定队伍时才需选车次；不指定时自动选队。旧 `/跑路了再见`、`/解散队伍` 继续兼容。
- **建队后 10 分钟清理，仅首次凑满 3 人时重新起算 10 分钟。** 首次满员通知 @ 当时 3 位成员并提醒接友谊。之后进队、离队、降至不足 3 人或再次满员都不延长截止时间。
- 普通入队提醒 @ 同车原有成员；离队提醒 @ 剩余成员；发送群号后 @ 除发送者外的同车成员；自动和手动解散提醒 @ 当时成员。
- 每群所有车次在**同一张面板**中展示，共用 **4 分钟**广播节奏，各车独立清理。标题使用正文加粗，自动清理和广播间隔同行，每车成员放在同一逻辑行；手机窄屏按 QQ 客户端自然换行。
- 保留头像和已等待时间，**移除当月胜率**且不再为面板查询战绩。面板成员姓名使用可点击填字标签：展示名字不额外加 `@`，点击填入 `@名字` 文字，面板更新和广播本身不 @ 成员。官方消息返回群名片时优先显示群名片，否则使用 QQ 昵称，均缺失时用车友标识；插件不能反向读取 QQ 原生 @ 标签在客户端显示的群名片。真正的成员提醒只在入队、离队、满员、发车、解散通知中发送。
- 底部按钮每行至多三个：进队等车／跑路了再见／发送群号，下一行再开一车／解散队伍／等车帮助，非冷却期间第三行显示“呼叫全体”，冷却期间的新面板隐藏该按钮，冷却结束后下次刷新恢复。发群号按钮只填入前缀，由用户补全确认发送。
- **呼叫全体**在同一条消息中发送原生 @全体成员友谊邀请、当前所有车次及完整等车面板，显示成员头像、姓名、等待时间和清理倒计时；无车时明确显示当前没有队伍。同群所有用户和车次共用30分钟冷却，重启、跨日、散队不会清零；发送前持久化，未确认送达也保留冷却且不自动补发。该入口不要求先入队，可在没有队伍时摇人开车。若使用平台指令勾选配置，需开放“呼叫全体”。[SDK 文档](https://zhinjs.github.io/qq-official-bot/api/group.html)注明机器人需为群管理员、每群每天限1次；插件冷却不替代 QQ 平台权限和每日额度，实际以 QQ 接口为准。
- 同一官方群内一人同时只能在一队，允许超过 3 人；已有队伍时“再开一车”创建空队伍。车次号按**北京时间每日从 1 起算**，跨日未结束的旧队保留并附日期，内部唯一 token 不重用。
- 发车时先发带真实 @ 的集合通知，再单独发送**纯数字普通文本群号**，不使用会填入输入框并 @bot 的指令链接。数字的下划线和号码操作弹层由 QQ 客户端自行识别，尚未进行真实 QQ 客户端验证。通知每个收件人只保留一个原生 @，删除额外的昵称填入链接。点击原生标签后的行为由 QQ 客户端处理，不保证自动填入消息框。
- 保留 `/等车`、`/蹲车`、`/我也要等车`、`/人齐了发车`、`/友谊等车帮助` 等旧入口。身份关联仍按 AppID 验证原 QQ，不改变角色/参赛 ID 归属；账号管理和其他功能继续在 SnowLuma 使用。
- 队列存档自动从 JSON v1 升至 v2，保留成员、token、关联和待发提醒；旧截止不被重新延长，最长剩余 10 分钟。提醒持久化后发送，失败每 4 分钟或新交互时补发。MySQL schema 仍为 v20。

详见 [友谊等车使用说明](OFFICIAL_QUEUE_GUIDE.md)。


### ➕ 追加轮次 (/第N轮)
- 读取群聊中最近一条战报，追加第 N 轮（支持 `/第二轮`、`/第3轮`，以及不带 `/` 的形式）；完整匹配轮次指令即可触发，无需额外 @ 或匹配全局对话前缀。平台指令配置仍需开放“第N轮”。
- 不带参数：从上一轮及本轮**空闲存活选手**中随机配对，跳过仍在 `0:0` 对局中的双方；同一选手不会在一次匹配中重复出场
- 本轮对局打完后先用 `/记录` 填比分，再发 `/第二轮` 可让胜者继续匹配；败者不再入池。若暂时凑不齐双方空闲选手，会提示先完成未结束对局
- 也可指定对阵或直接记比分：`/第二轮 云玩家 2:0 鸽子`

### ✏️ 记录比分 (/记录)
- 按玩家名填入比分，不用重发整段战报
- `记录 云玩家 20`（填入云玩家最后一场未记录的对阵，`20` 即 `2:0`）
- `记录 云玩家 20 鸽子`（无未记录对阵时插入最新轮次）

### 📤 提交战报 (/发送)
- 粘贴填好比分的战报即可入库（`/战报` 仍可用）
- 支持**回复引用**战报消息，也支持一次粘贴**多份**逐份入库
- **友谊赛与踢馆都走这里**，按首行自动识别（`战队: A VS B` / `A踢馆B`）
- 自动判定胜负并回复**战报 ID**（用于删除）、逐场对阵结果
- 校验：战报必须包含本群绑定的战队；对局数不足 `min_duels`（默认 3）视为未完成；
  胜负未定会拒收并列出未填的对局
- **重复提交会拒收**：内容一模一样的战报再次提交时，会提示已有记录及其 ID
  （换个人提交、或在同一战队的另一个群再贴一遍，同样按重复处理）
- **禁止私聊提交**，包括超管；只有群聊属性为**战报群**的群可以提交（含引用、批量、踢馆报）
- 完成战队及群属性设置后，主群、友谊群仍可查询；战队管理员或超管先用 `/群聊属性 战报群` 设置提交群
- `战队:`、`战队：` 两种冒号均支持粘贴、引用、批量拆分和读取最近战报

### ⚔️ 踢馆 (/踢馆)
- `/踢馆` — 本战队本月踢馆卡（踢馆成功 / 守馆成功 / 守馆首轮 / 踢馆成功含馆主 + 徽章 + 积分）
- `/踢馆 云玩家` — 单选手的踢馆卡，末尾也可加月份，如 `/踢馆 云玩家 七月`
- 踢馆积分独立统计，与友谊积分**合计**为「总积分」

### 🏆 排行榜 (/排行)
- `/排行` — 本战队个人积分榜（图片表格，显示全部队员）
- `/排行 队伍` — 本战队对战各对手的记录
- `/排行 全部` — 全战队选手榜
- 图片和点评均通过 AstrBot 标准回复流程发送，图片生成失败时使用文字榜单。`getaddrinfo EAI_AGAIN htdata3.qq.com` 表示 SnowLuma 所在环境的 DNS 解析异常，需要在部署环境恢复解析；插件不会修改 DNS 或把上传失败视为图片已发送。
- 排行榜共 14 列：总积分｜友谊积分｜踢馆积分三个分数列，外加**守馆成功 / 守馆首轮 / 踢馆成功**三个次数列（在「无双次数」之后），**按总积分排序**
- **所有列居中**（文字表格与图片表格一致）
- **该月已结算过**时，末尾多一列「奖金」（共 15 列）；没结算过的月份不显示这列
- **图片最左侧有「战队战绩」面板**（8 行，左边名称右边数值）：总场数 / 守馆首轮 / 守馆 / 踢馆 / 胜场 / 负场 / 胜率 / 积分。只有 `/排行` 个人榜有，`/排行 全部` 是跨队榜，不给
- 末尾可加月份，如 `/排行 七月`
- 配置点评人格后，榜单发出后会附上简短的一段点评，不带标题；本队个人榜、全战队个人榜、队伍对战记录都支持，图片或文字展示均可。
- 在插件配置的 **插件 AI 人格**（`ai_persona_id`）下拉框中，可选择 AstrBot 已配置的人格。插件内 AI 功能共用这一套，所有群一致；留空只显示排行，不调用模型，也不发送点评提示。模型继续使用 AstrBot 当前会话配置，无需另填 API Key。`ranking_ai_comment` 默认开启，可按需关闭。
- 观点与语气由 AI 和人格自由发挥，只要求简短、单段、不加标题。传入本次同月份榜单展示的全部条目；全战队图片已截断时传入图中展示的条目。模型异常会给出简短提示，排行仍正常显示。

### 💰 月度结算 (/结算、/重置结算)

**超管、战队管理员或群管理/群主** —— 结算并发奖金：

- `/结算` — 不给月份就是**上个月**（刚过完的那个月）
- `/结算 7月` — 给该月积分榜**前 4 名**发奖金
- `/结算 7月 12` — 追加奖励到第 12 名
- `/结算 7月 8月 9月` — 一次结算多月，各月奖励前 4 名；`/结算 7月 8月 9月 12` 则各月奖励前 12 名
- 月份支持中文及逗号分隔，例如 `/结算 七月、八月 12`；重复月份只算一次。各月独立排名、计算奖金，本次结果在同一事务中保存；没有可结算战绩的月份会跳过，保留原快照。
- 奖金 = **总积分 × 3**，按名次封顶，结果**向下取整**（34.17 → 34，只舍不入）：

| 名次 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9~12 |
|---|---|---|---|---|---|---|---|---|---|
| 上限 | 130 | 100 | 80 | 50 | 40 | 35 | 30 | 25 | 15 |

- **只能结算已经结束的月份**（当月结算会被拒绝）；1 月里写 `12月` 会自动落到**去年** 12 月，回执里会写明是哪一年
- 重跑就是**覆盖重算**：旧奖金作废，`/结算 7月` 一律回到前 4 名
- 结算**不改变任何排行数字**，奖金只是从总积分派生的展示值；只给自己战队的选手发
- 每次管理人员成功结算后，在**执行命令的群里发布一条 QQ 群公告**，包含本次所有成功结算月份的获奖人、奖金、各月合计，以及每人本次领取合计，提醒找战队管理员领取。重跑仍会发布本次公告。
- 机器人 QQ 需要该群的公告发布权限，通常需设为群管理；公告开启弹窗及确认收到。发布失败不会回滚已保存结算，会单独提示；超时则提示结果未确认，不自动重发。
- 群消息中的 @ 仍只在该月首次结算或获奖名次变化时发送，同一个人在本次命令中只提醒一次；绑定了 QQ 才能真正 @ 到。

**重置结算** —— 把某个月打回「未结算」，重来一次：

- `/重置结算` — 重置**上个月**；`/重置结算 7月` — 重置 7 月
- 删掉该月的结算记录：`/排行 7月` 不再显示「奖金」列，`/结算 7月` 会变回「该月尚未结算」
- 该月**本来就没结算过**时只回一句「无需重置」，不报错
- 重置后重新 `/结算`，会被当成**该月第一次结算** —— 会重新 @ 一遍获奖成员
- 每次只重置一个月份；只影响本战队，别队别月不受影响

**其他人** —— 同一个命令是**只读查询**，不会改动任何数据：

- `/结算` — 查看**上个月**已结算的名单与金额；`/结算 7月 8月` 一起查看指定月份，不发布群公告
- 该月**还没结算过**就只回「该月尚未结算」，不会预览「如果现在结算会发多少」
- 查询**只读数据库里的结算记录**，不重算、不覆盖，也不受榜单事后变动影响

### 📩 好友申请与入群邀请审批

先配置 `super_admin` 为超管 QQ，并确保超管能收到机器人私聊。收到好友申请或邀请机器人入群时，机器人会私聊转发申请人 QQ、验证消息；群邀请还会带上群号、群名，昵称和群名查询失败时仍会转发号码。

超管引用通知回复 **同意** 或 **拒绝** 即可处理。只有一条待处理申请时，也可以直接私聊回复这两个词；有多条时需引用对应通知，或带上编号：

```text
同意 A1B2C3D4
拒绝 A1B2C3D4
```

私聊 `/申请列表` 可查看当前机器人的待处理申请。此功能仅对插件配置中的超管开放；只出现在 `/帮助 超管` 中。

处理入群邀请后，机器人会私聊告知原邀请人“同意”或“拒绝”的结果，并附上群号。QQ 明确返回已同意时，通知也按实际已同意发送。审批失败或结果未确认时不通知成功；通知发送异常会提醒超管手动告知。重复审批或重启不会重复发送结果通知。

旧邀请审批失败、再次邀请没有新通知时，超管私聊 `/刷新申请`，或 `/刷新申请 A1B2C3D4` 指定旧编号。插件会从待处理邀请人的最近消息中找回对应群的原始邀请卡，发送通知；再引用这条通知回复同意或拒绝。无需先删除旧记录。

- 适用于 AstrBot 的 `aiocqhttp` OneBot V11 适配器及 SnowLuma。
- 申请保存在插件数据目录 `request_reviews.json`，重启后可继续处理，不依赖 MySQL。
- 重复事件只转发一次，已经处理的申请不会重复执行；接口明确失败时可以重试。
- SnowLuma 支持从私聊原始入群邀请卡读取本次邀请；同群再次邀请有新序号时会发送新通知，旧编号提示处理最新通知。
- QQ 明确返回“已同意”时同步为已处理；此后再拒绝会提示已同意，不会误报拒绝成功。
- 引用兼容原始消息 ID 和 AstrBot 的引用组件；ID 变化时会核验平台提供的原通知内容，保留旧通知兼容。平台无法取回原消息时，可按编号处理。
- 平台拒绝处理时会显示具体原因，完整异常进入 AstrBot 插件日志。
- 审批调用超时或进程在处理中退出时，列表会显示“需核实”，请到 QQ 确认结果。
- 只处理好友申请和邀请机器人入群，不处理群成员的加群申请；群内回复不会执行审批。

**SnowLuma v1.14.11：** 旧申请返回 `120161001 / handle async message fail` 时，可先使用 `/刷新申请` 找回邀请卡，不直接修改旧申请的类型或序号。刷新只检查当前机器人待处理群对应的邀请人，每次最多 10 位，每位最近 100 条好友消息；只提取原始邀请卡，不接收转发节点、普通群名片或其他群的卡片。原始卡片带有本次邀请的实际审批序号；旧编号保留并提示处理新通知，不会自动审批。找不到卡片时仍需重新发送入群邀请。此路径已按 v1.14.11 源码与模拟接口验证，仍需实际 QQ 验证；该错误本身不能证明邀请已失效或已处理。

QQ 返回 `120162004 / already agree msg by self` 则明确表示该申请已被同意，插件会同步状态并移出待处理列表。

### 战队管理员的设置与权限

超管先配置自己的 `super_admin` QQ，然后可以执行：

```text

/设置战队管理员 a队 123456789,987654321

`设置` 是**覆盖本队名单**：第二条示例授权两人，再执行第一条就只保留一人。
可在战队还未绑定任何群之前授权。其他战队的管理员名单不受影响。

| 身份 | 绑定战队、群聊属性 | 管理 ID、解绑他人 ID、删除战报、结算与重置 |
|---|---|---|
| 超级管理员 | 可设置任意群，无需本队授权 | 可操作 |

------第一轮------
云玩家  0:0  柠檬
遗老  0:0  鸽子
萌新  0:0  复读机
------第二轮------
```

```

------第一轮------

遗老  1:2  鸽子
萌新  2:0  复读机
```

> 也可以直接**回复引用**那条战报后发 `/发送`。

### 提交一份踢馆战报

踢馆是一队打另一队的馆：踢馆方要从头打穿全部防守者，守馆方只要终结踢馆者一次就算守住。
首行写 `A踢馆B`（左=踢馆方，右=守馆方），**没有轮次分隔**、时间行也不带前缀：

```
/发送
a队踢馆b队
规则：OCG.2026.7.1.MATCH
2026.8.30 21:00
踢馆开始！
云玩家 2:1 复读机
云玩家 2:0 鸽子
云玩家 2:1 柠檬
云玩家 2:1 路人甲
云玩家 2:1 路人乙(馆主)
```

- 最后一场谁赢就是谁赢：上面这场最后一场 `云玩家` 胜 → **踢馆成功**
- 机器人回执**整段说法跟着提交方走** —— 本群在右侧（守馆方）逐局是
  `云玩家 2:1 路人乙(馆主) ❌ 防守失败`、末行结论是 `🛡️ 守馆成功（b队）`；
  本群在左侧（踢馆方）则是 `✅ 进攻成功`、末行 `⚔️ 踢馆成功`，
  **被馆主终结时写 `💀 踢馆失败（a队）`，不会显示成对手守馆成功**
- 防守方名字后加 `(馆主)` 表示这局是馆主在守
- 没人守馆就写占位行 `云玩家 0:0 规则`（防守方名字就叫 `规则`）

### 追加轮次 / 逐条记比分

```
/第二轮                  # 匹配上一轮及本轮空闲存活选手
/第二轮 云玩家 鸽子        # 指定两人对阵
/第二轮 云玩家 2:0 鸽子    # 直接记比分

/记录 云玩家 20            # 填入云玩家最后一场未记录的对阵
/记录 云玩家 20 鸽子       # 无未记录对阵时插入最新轮次
```

> 追加轮次需要上一轮**已填好比分**才能确定胜者。

## 💡 几个概念

- **`0:0` 是占位**，表示还没打，不是平局（平局是 `1:1` 这类）
- **替补**：ID 后加 `(替)`；此外第一轮没出场、后续才出场的选手也自动算替补
- **判罚**：ID 后加 `(规则)`，判罚方比分必然更低（即败方）
- **友谊积分** = 胜场 × 胜率（只算友谊赛）；**友谊次数** = 参与的比赛场次；**无双次数** = 一人击败对面全部选手的场次
- **总积分** = 友谊积分 + 踢馆积分（排行榜按总积分排序）
- **守馆成功 / 守馆首轮 / 踢馆成功** 是**次数**不是分数，排行末三列就是它们
  （首轮被终结会同时记一次守馆成功和一次守馆首轮，所以两个数会一起涨）
- **踢馆积分**：踢穿 ≥4 名防守者守的馆 +3，1~3 名 +2，无人守馆 +0（只发徽章）；
  馆也在守再 **+2**（所以 4 人 + 馆主 = 5 分）
- **守馆积分**：守馆成功次数 ÷ 3 **向上取整** + 守馆首轮次数 ÷ 3 **向上取整** + SHUT DOWN × 5，
  **本月上限 10 分**。首轮被终结同时算一次守馆成功和一次守馆首轮
  （向上取整的意思是守馆成功 1 次或 2 次就已得 1 分，不必凑够 3 次）
- **SHUT DOWN**：馆主作为**第 5 个**守馆者出场并终结踢馆者，+5
- 同一个月的踢馆积分**重复踢穿同一战队不累计**，只取最高分的那场；踢不同队才累计
- **结算是快照**：把结算那一刻的榜单前 N 名连同总积分、奖金存下来。之后补录战报让排名变了，
  已发出去的奖金**不会自动跟着改** —— 要更新就重跑 `/结算`（覆盖重算）。
  所以 `/排行` 上显示的「奖金」列是**结算时的结果**，未必与当前名次一一对应
- **排行榜图片左侧面板上的「守馆首轮 / 守馆 / 踢馆」是各自赚了多少的原始分量**
  （次数 ÷ 3 向上取整、踢馆加点），**不套上面那个 10 分月度上限**；上限只体现在面板最后一行
  「积分」上。所以守馆多的月份里，这三行加起来会**大于**「积分 − 友谊积分」
- **踢馆与友谊互不干扰**：踢馆对局不进胜负、友谊次数、无双、趋势图等友谊口径；
  踢馆报的时间、队标同样按战队跨群统计（守馆方也能查到自己的守馆积分）
- 统计按**战队跨群聚合** —— 同一战队的多个群，数据会合并
- 默认统计**本月**，可加 `X月` 或 `最近N天`
- 统计命令（`/排行` `/战绩` `/趋势` `/导出`）要求本群已绑定战队，且明确选择了群属性，
  不完整时返回开通流程，避免数据被算到别的战队头上

## 📦 安装说明

[下载 v1.26.4 安装包](https://github.com/1443290403/astrbot_plugin_battle_report/raw/refs/heads/install-packages/astrbot_plugin_battle_report-1.26.4.zip)，在 AstrBot 插件管理中上传。包内根目录直接包含 `metadata.yaml` 和 `main.py`。

1. 将本目录放到 `AstrBot/data/plugins/astrbot_plugin_battle_report`
2. 重启 AstrBot，在管理面板启用插件
3. 填写 MySQL 配置及自己的 `super_admin` QQ，插件会自动迁移到数据库 v18
4. 超管用 `/设置战队管理员 a队 123456789` 指定战队管理员（也可私聊发授权命令）
5. 超管或该战队管理员在目标群用 `/绑定战队 a队` 绑定战队
6. 超管或该战队管理员按用途执行 `/群聊属性 友谊群`、`/群聊属性 战报群` 或 `/群聊属性 主群`
7. 设置后机器人立即发送对应流程；战报仅在设置好的战报群内 `/发送`

所有命令使用 `/` 前缀（AstrBot 默认唤醒前缀即为 `/`，无需额外配置）。

## ⚙️ 配置说明

| 配置 | 默认 | 说明 |
|---|---|---|
| `mysql_host/port/user/password/db` | — | MySQL 连接信息（必填） |
| `super_admin` | 空 | 超级管理员 QQ，需自行填写；留空禁用超管命令。旧配置不会自动替换，请检查 |

| `trend_chart_width` / `height` | `960` / `480` | 趋势图尺寸（px） |

## QQ 申请诊断脚本

审批失败时，在运行 AstrBot 的服务器执行：

```bash
python3 scripts/diagnose_qq_requests.py
```

自动检查宿主机常见数据目录和运行中的 AstrBot Docker 容器，输出最近 8 条申请的编号、状态、source、request_time、审批序号及 event_type。QQ、群号、昵称、验证消息、通知全文及原始不透明 flag 不会输出；同一个群或邀请人可用脱敏引用值关联。

可指定容器、文件或申请编号：

```bash
python3 scripts/diagnose_qq_requests.py --container astrbot --token A1B2C3D4
python3 scripts/diagnose_qq_requests.py --path /AstrBot/data/plugin_data/battle_report/request_reviews.json
```

工具只读取 `request_reviews.json`，Docker 检查只执行 `docker ps` 与容器内的同一只读脚本，不加载插件、不连接 MySQL/QQ、不修改申请状态。脚本须保存为文件运行，才能自动在容器内执行；无法定位时可使用 `--container` 或 `--path`。脚本独立运行，无需先更新插件。

## 战报核对 WebUI

需要 **AstrBot 4.27.3 或以上**。更新并重载插件后，在 AstrBot 后台进入 **插件 → 战队对战战报 → 插件详情 → 战报核对**。页面沿用后台登录，不需要额外开放端口、输入数据库密码或配置令牌。

选择本地战队与比赛月份，点击“开始核对”；也可展开“网站查询地址与发布时间范围”，粘贴 `rep.ygobbs2.com` 的搜索结果地址并点击“读取地址”。默认比赛月份为北京时间的上个月；网站队名与本地战队名不同时可分别填写。

- 展示内容匹配、网站独有、本地独有、内容差异候选、网站/本地重复、胜负不一致、网站胜负待核、解析失败、比赛日期越界及其他队名记录。
- 可按分类分页查看双方原文、复制文本、导出完整JSON、取消运行；保留最近20次核对。抓取进度按页显示，重启中断的任务不会自动重跑。
- 本地按 `home_team` 跨群读取，只比较友谊战报；网站按**发布时间**搜索，本地按**比赛日期**查询。晚发布的战报可扩大网站发布时间范围后再查。网站未检出、同日同地点多场和条数不同均只是核对线索，不自动认定为虚假或重复。
- 完整抓取后按网站 ID 写入独立 `cloud_battle_reports` 表；相同 ID 更新正文及最后抓取时间，不重复插入，也不自动导入本地战绩。网页内容以纯文本显示，接口由 AstrBot 后台登录保护。
- “本地战报”直接查询已上传的友谊和踢馆记录，可按类型过滤；“云端战报”查看已归档的网站记录，无需重新抓取。两类列表均直接展示全文，支持分页和跨页勾选；“查询战队胜负”可选择全部／胜场／负场，按筛选后总数分页，未知胜负不算负场。战报区域与搜索栏等宽，同排卡片等高，外侧分页不挤占内容宽度。默认打开本地战报；战报容器两侧的箭头可翻页，首页／末页禁用对应箭头；右箭头左侧页码栏最多同时显示10页，可滚轮浏览更多页码并点击跳转。每份的“复制全文”只复制战报正文，不带勾选状态、编号、上传信息或其他页面文字。
- 勾选后点“发送到 QQ”，选择 SnowLuma／OneBot 连接、自定义 QQ 或目标战队的指定管理员，预览正文和收件人，再确认发送。每份战报一个合并转发节点，每包最多50份；官方机器人不能通过数字 QQ 号私聊发送。
- 发送记录按收件人和分包保存回执；已确认成功的包不会重复发送。超时、断连等结果未确认时需先在 QQ 核实，系统不自动重发。此回执不修改原人工“已发送”标记、比分、指纹或排行。
- 需要 AstrBot 容器能访问 `https://rep.ygobbs2.com/`。每次核对重新抓取，不复用旧网页；单页超时15秒、最多尝试2次、页间隔0.5秒，总时限5分钟。单次日期范围最多93天、最多200页/10000条；分页异常或抓取失败时不发布残缺差异结果。

具体使用步骤与范围解释见[战报核对使用说明](REPORT_COMPARISON_GUIDE.md)。

## 数据核对脚本

用于排查「插件统计结果与实际对战结果不一致」：把线上战报系统（rep.ygobbs2.com）
的区间数据抓下来，与插件库比对。两个脚本仍可独立运行；v1.28.0 起与 WebUI 共用 report_site / report_comparison 的解析与比对逻辑。

| 脚本 | 作用 |
|---|---|
| `scripts/crawl_battle_reports.py` | 爬取指定区间的战报 → 导出 JSON/CSV，并按**正文内容**标注「完全一样的战报」重复组 |
| `scripts/diff_battle_report_db.py` | 读导出的 JSON + 连库（**只读 SELECT**）→ 输出差异报告 |

比对**只针对友谊战报**（`matches.kind = 'friendly'`）——线上战报站只收录友谊赛，
踢馆报拿进来只会全部落进「只在库里有」。插件自己的统计查询也是这么过滤的。
需要连踢馆一起看时加 `--include-raid`。

比对报告保留库里缺失、只在库里有、库内重复、网站侧重复、胜负不一致、同日同队同地点多版与条数差异提示。网站发布范围不等于当天全部比赛，条数不同不能证明同一场被记了两遍，需结合原文和发布时间核对。

```bash
# 1. 爬取（将目标群名和日期换成实际值）
python scripts/crawl_battle_reports.py --group "目标群名" --start 2026-09-01 --end 2026-09-30 --refresh

# 2. 比对（连库参数默认取 ASTRBOT_MYSQL_HOST/PORT/USER/PASSWORD/DB 环境变量）
python scripts/diff_battle_report_db.py
python scripts/diff_battle_report_db.py --dry-run      # 只打印摘要，不写报告
```

产物写入 `scripts/output/`（已 gitignore）：导出的 `.json`/`.csv`、原始 HTML 缓存
`raw/<查询指纹>/`（按战队和查询日期隔离）、差异报告 `diff_*.md`/`.json`。

> 注意：线上查询的 `starttime/endtime` 过滤的是**发布时间**，不是战报正文里的
> **比赛时间**，两者可能不同月，脚本会标注越界的记录。站点响应不稳定，爬取对每页
> 做校验与重试，任一项最终失败即整体放弃导出（不会产出缺页的数据）。

## 独立战报管理入口

v1.30.1 起安装／更新／启用插件后自动注册页面。在当前 AstrBot 后台访问地址后加 `/battle-report/` 即可，例如后台为 `http://服务器IP:6185` 时，入口就是 `http://服务器IP:6185/battle-report/`。不需要打开后台导航，不需要手动导出、配置 Nginx 或开放新端口。

使用原 AstrBot 管理员账号及可选两步验证；内置入口沿用当前后台的 HTTP／HTTPS，查询、核对、复制、下载和 QQ 发送继续使用原受保护 API，匿名用户只能看到登录页及静态文件。JWT 仅在内存，401 后重新登录再手动重试，不自动重放操作。AstrBot 仍需在线，账号权限等同原后台，没有独立战队账号与服务端战队授权。

页面随插件版本更新，重启自动恢复；停用／卸载清理本实例路由，不修改 AstrBot／Nginx／Docker 配置文件。适配 AstrBot >=4.27.3 的 FastAPI 兼容层，若框架接口不兼容会记录提示并保留原 Pages 入口。独立域名或单独静态站点仍可选用原导出脚本与 Nginx 模板，详见 [部署指南](STANDALONE_WEBUI_GUIDE.md)。
